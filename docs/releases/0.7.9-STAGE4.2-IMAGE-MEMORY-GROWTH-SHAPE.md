# v0.7.9 Stage 4.2 - Image Memory Growth Shape

## Scope and method

This validation characterizes the shape of the memory footprint from the fixed Stage 3.4/3.6 20-title manifest (`lmm-v0.7.8-production-validation-fixed-sample-v1`). It does not modify production sync logic, UI, settings model, schema, or MediaStorage behavior.

All runs used the local MetaTube Provider (`127.0.0.1:8080`) and the same ordered manifest. Each run copied `baseline/LocalMediaManager.db` and configured a run-local `MediaStorage`; no formal database, formal media directory, NAS, or deployment directory was opened. Before every re-run batch, only the copied database's provider metadata and run-local media were reset. This forced a new image request set while retaining the same Bridge process for the same-process experiments.

For every reported stage: wait 30 seconds, request Full GC, wait 30 seconds, then capture runtime memory and a native HeapWalk. All reported HeapWalk results had `complete=true`, `walkSucceeded=true`, and finite non-negative `busyBytes`.

## Growth slopes

Same-process deltas use the preceding settled stage. `image delta` uses the difference in downloaded-image counters.

| Transition | Pvt delta MiB | Pvt MiB/movie | Image delta | Pvt MiB/image | Native busy delta MiB |
|---|---:|---:|---:|---:|---:|
| Startup -> 1 | +8.262 | +8.262 | 12 | +0.689 | +1.205 |
| 1 -> 5 | +7.332 | +1.466 | 63 | +0.116 | +1.194 |
| 5 -> 10 | +12.836 | +1.284 | 126 | +0.102 | +1.079 |
| 10 -> 20 (first) | +25.949 | +1.297 | 215 | +0.121 | -0.751 |
| 20 first -> second | +3.730 | +0.187 | 215 | +0.017 | +0.290 |
| 20 second -> third | -0.558 | -0.028 | 215 | -0.003 | +0.403 |

The second 20-title increment is 14.4% of the first 20-title increment (+3.730 versus +25.949 MiB), and the third increment is negative. For native busy memory, the corresponding increments are +0.290 and +0.403 MiB, both small and non-linear compared with prior work. This is not a sustained linear private-memory or native-busy slope.

The auxiliary disabled curve increased +2.312 and +2.832 MiB after its first batch. Because it had a different NoResult result set, it cannot prove that this residual non-image growth is caused by or independent from the image path.

## Interpretation

The best-supported shape is **first-batch growth followed by a platform/high-water mark** for the full image-enabled pipeline. It is not consistent with cross-task, per-image linear accumulation: the same Bridge processed a further 430 downloaded images after the first 20-title stage, while settled private memory stayed within +3.730/-0.558 MiB and all image HTTP lifecycle counters returned to zero.

This does not identify a concrete leaked object or call site. The Stage 3.6 result remains a **Root Cause Level 2** finding: image-path work has a substantial high-water cost, but Stage 4.2 does not establish a persistent HTTP response, stream, image buffer, decode, hash, or file-write retention issue. The Stage 4.1 static audit and balanced lifecycle counters further weigh against an HTTP response lifetime leak.

## Memory Gate and repair decision

**Memory Gate: BLOCKED.** The gate remains blocked because the existing Stage 3.6 baseline threshold has not been redefined or accepted. This experiment recommends evaluating an explicit high-water initialization allowance rather than proceeding directly to a leak fix.

**Minimal repair conditions: not met.** Although image work correlates with the large first-workload cost, the second and third equivalent batches do not maintain stable growth, and no lifecycle or duplicate-buffer defect was identified. No production change is proposed or applied.
