## Conclusion

`CONDITIONAL PASS - Additional Investigation Required`

The Stage 3 functional result remains valid, but Human Acceptance and the 1,370-title production sync remain blocked.

The measured growth is not a managed leak, Provider cache, task-result cache, task-log cache, handle leak, thread leak, or SQLite pool retention. It is non-managed process-private retention strongly associated with the image download and image validation/decode path. The current evidence does not prove a safe production-code fix, so this stage deliberately does not introduce a speculative behavior change, per-task GC, process restart, or image-download disablement.

## Root-Cause Classification

**Primary:** `Native Memory Retention` in the image download / image validation-decode workload.

**Evidence:**

- The normal run retained +113.4 MiB between two identical 100-title batches after full GC.
- The no-image control retained only +15.9 MiB under the same Provider, Merge, Writer, SQLite, NFO, task, and Bridge process conditions.
- `ImageFileValidator` is the only per-downloaded-image decode path and currently uses `SkiaSharp.SKCodec`.
- HTTP responses, response streams, destination streams, SQLite connections, commands, readers, and `SKCodec` are already explicitly scoped with `using` / `await using` in the inspected paths.
- Full GC reduces working set but does not materially reduce the retained private-memory platform; GC heap, LOH, and POH are small and stable.
- Clearing `SqliteConnection` pools reduced handles (for example 747 -> 717) but changed private memory by approximately 0 MiB. SQLite pooling is not the primary cause.
- Handles and threads return near their initial post-start values; there is no evidence of a linear handle or thread leak.

**Not proven:** a specific SkiaSharp allocator defect or a safe cache-purge/replacement strategy. The investigation therefore does not claim a disposal bug and does not change image validation semantics.

## Follow-Up Experiments

### Header-reader equivalence experiment

`ImageFileValidator` was temporarily changed in the isolated build to use a bounded JPEG/PNG/WebP/GIF header reader instead of `SKCodec`. The new reader matched Skia's format and dimensions for 4,235 existing Stage 3.1 downloaded resources and for generated JPEG, PNG, WebP, and GIF test images. The temporary production change was then removed because it did not solve the retention gate:

| Run | Batch 1 private MiB after full GC + idle | Batch 2 private MiB after full GC + idle | Delta |
|---|---:|---:|---:|
| Header-reader experiment | 373.5 | 472.0 | +98.5 |

This rules out `SKCodec` header creation as the primary cause. The experiment did not alter any committed synchronization behavior.

### Windows virtual-memory classification

The validation-only runtime endpoint now aggregates committed `VirtualQuery` regions. The fourth isolated two-batch run showed that the retained growth is `MEM_PRIVATE`, not mapped file or module-image memory:

| Snapshot | Process private MiB | MEM_PRIVATE MiB | MEM_MAPPED MiB | MEM_IMAGE MiB |
|---|---:|---:|---:|---:|
| Bridge ready | 171.4 | 162.8 | 154.0 | 129.4 |
| Batch 1, full GC + idle | 363.8 | 354.9 | 170.6 | 149.8 |
| Batch 2, full GC + idle | 480.8 | 471.7 | 171.4 | 149.8 |

The second batch retained an additional 116.8 MiB of `MEM_PRIVATE`, while `MEM_MAPPED` and `MEM_IMAGE` remained effectively stable. This strengthens the classification to native private-memory retention, but does not identify the allocating library or call stack.

### Native heap tracing limitation

Windows Performance Recorder is installed, but `wpr -start Heap -start VirtualAllocation -filemode` was rejected with `0x80070005 Access is denied` in the current non-elevated process. No ETW trace was started and no production or validation sync was launched as part of that failed attempt. An elevated local WPR session, or an equivalent native-heap profiler, is required for allocator-level attribution.
