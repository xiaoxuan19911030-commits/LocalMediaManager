## Conclusion

`CONDITIONAL PASS - Additional Investigation Required`

The Stage 3 functional result remains valid, but Human Acceptance and the 1,370-title production sync remain blocked.

The measured growth is not a managed leak, Provider cache, task-result cache, task-log cache, handle leak, thread leak, or SQLite pool retention. It is non-managed process-private retention strongly associated with the image download and image validation/decode path. The current evidence does not prove a safe production-code fix, so this stage deliberately does not introduce a speculative behavior change, per-task GC, process restart, or image-download disablement.

## Root-Cause Classification

**Primary:** `Native Memory Retention` in the image download / image validation-decode workload.

**Evidence:**

- The normal run retained +113.4 MiB between two identical 100-title batches after full GC.
- The no-image control retained only +15.9 MiB under the same Provider, Merge, Writer, SQLite, NFO, task, and Bridge process conditions.
- `ImageFileValidator` is the only per-downloaded-image decode path and currently uses `SkiaSharp.SKCodec`.
- HTTP responses, response streams, destination streams, SQLite connections, commands, readers, and `SKCodec` are already explicitly scoped with `using` / `await using` in the inspected paths.
- Full GC reduces working set but does not materially reduce the retained private-memory platform; GC heap, LOH, and POH are small and stable.
- Clearing `SqliteConnection` pools reduced handles (for example 747 -> 717) but changed private memory by approximately 0 MiB. SQLite pooling is not the primary cause.
- Handles and threads return near their initial post-start values; there is no evidence of a linear handle or thread leak.

**Not proven:** a specific SkiaSharp allocator defect or a safe cache-purge/replacement strategy. The investigation therefore does not claim a disposal bug and does not change image validation semantics.
