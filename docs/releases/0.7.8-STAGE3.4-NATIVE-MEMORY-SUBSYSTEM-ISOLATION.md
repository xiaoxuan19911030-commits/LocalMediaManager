# v0.7.8 Stage 3.4 Native Memory Subsystem Isolation

## Status

Corrected HeapWalk evidence reaches Root Cause Level 2: the image-download resource
subsystem is strongly associated with retained process-private memory. HeapWalk does
not identify a specific allocator or call site, so this is not Level 1. No production
sync logic was changed.

## Reproducibility

The local MetaTube service at `127.0.0.1:8080` was listening and returned HTTP 200
before this run. Two independent fixed-20 isolated runs used the same baseline and
sample manifest.

This evidence used the Release binaries already present in the existing dirty

### Optional Metadata Classification

Director and series are optional metadata. A missing value is `Not Applicable` when
the source did not provide that field; it is not a warning, a missing-field failure,
or a `NoResult` reason. A field supplied by the source but absent from its target
relation is a `Write Failure`. A relation that existed before synchronization and is
absent afterward is a `Data Regression`.

After this rule was added, a local re-verification of `repro-20-a` found one director
data regression: `THU-063` had one director relation before the run, completed the
sync task, and had zero afterward. This does not change the two expected `NoResult`
classifications, but it means the run cannot be used as a clean functional regression
pass. Series had no write failure or data regression in that run.

## Corrected HeapWalk Fixed-20 Rerun

### Interop Correction And Invalidated Data

The original `PROCESS_HEAP_ENTRY` mapping read `cbData` at pointer width and read
`wFlags` at the wrong offset. Its `busyBytes = Int64.MaxValue` values are invalid
and are excluded from all conclusions. The validation-only mapping now uses the
native pointer, 32-bit `cbData`, byte fields, `wFlags`, and trailing union layout.

The five corrected runs below each used a new Bridge process, a copied isolated
database, isolated MediaStorage, the fixed 20-title manifest, 30 seconds idle before
Startup, 30 seconds idle after task completion, Full GC, 30 seconds idle before
AfterGc, and a second immediate HeapWalk. The formal database, NAS, installation
directory, and 1370-title sync were not accessed.

Every HeapWalk sample had `heapCount=7`, `complete=true`, `walkSucceeded=true`, a
null Win32 error code, and finite non-negative counters. `busyBytes` was below both
the corresponding `MEM_PRIVATE` commitment and process private memory. Full raw
samples, including busy/free entry counts, bytes, largest blocks, handles, threads,
managed heap, error code, and interruption location are stored only in the ignored
isolation artifacts under `artifacts/validation/v0.7.8-stage3.4-subsystem-isolation/`
in each `heapwalk-fixed20-*/evidence/heapwalk-snapshots.json`.

The two full baseline runs have an AfterGc busyBytes range of 0.03%; the three
image-disabled runs have a 0.45% range. The small HeapWalk delta is more sensitive
to independent startup allocations, but its direction is consistent: mean baseline
delta is +2.628 MiB and mean image-disabled delta is +1.070 MiB, a 59.3% reduction.
The materially larger process-private delta is also stable: +79.560 MiB with images
versus +43.637 MiB without images, a 45.2% reduction. Provider outcomes are
comparable in every run: 18 metadata successes, the same two expected NoResult
classifications, and zero failures. The lower memory result is therefore not caused
by lower provider coverage.

### Image Processing Split

The required third experiment, download and stream-to-disk while bypassing decode
and hash validation, was not run. No existing diagnostic switch expresses that
behavior. Adding it would modify the production image-processing path, which this
Stage 3.4 rerun does not authorize. Consequently the data distinguishes image
download/resource processing from metadata-only work, but does not distinguish HTTP
buffering and file writes from `SKCodec`, format validation, or SHA-256.

### Root Cause And Repair Gate

**Root Cause Level: Level 2 (image-download resource subsystem).**

The corrected runs satisfy complete HeapWalk, finite and repeatable samples, a
single-variable reduction above 30%, and comparable successful task counts. They do
not locate a concrete allocator or sufficiently small behavior-preserving repair.
No production repair is authorized in this stage. The Memory Gate remains blocked;
this evidence does not authorize 100x2 confirmation, Human Acceptance, deployment,
or formal full synchronization.

## Static Lifecycle Audit

`MovieImageImporter` streams image responses to a temporary file and disposes the
response, source stream, and target stream. `ImageFileValidator` then opens that
file, creates an `SKCodec`, and performs a second sequential read for SHA-256.

The original native-heap snapshot is not usable for allocator attribution. Its
`PROCESS_HEAP_ENTRY` interop mapping read `cbData` at pointer width and read
`wFlags` at the wrong offset, which produced `busyBytes = Int64.MaxValue` in both
experiments. The corrected fixed-20 rerun above replaces those invalid values; it
does not identify a specific allocator.

The next required split is download-and-stream-to-disk without `SKCodec` validation
or hashing. No existing isolated harness switch expresses that behavior. Adding one
would alter the Bridge image-processing path, which is prohibited until a specific
allocator is located; it was therefore not implemented.
